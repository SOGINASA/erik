# Подготовка данных для модели рассмотрения заявок

Система собирает данные; модель пока не обучается, не выставляет метки и не выдаёт
рекомендации. Решения по доступу и публикации по-прежнему принимают проверяющие.

## Что заполняет пользователь

К существующим формам добавлены именованные вопросы с `formVersion=1`:

| Вид | Ключ `kind` | Дополнительные ответы |
|---|---|---|
| Создание сбора | `gathering` | `purpose`, `volunteerTasks`, `safetyPlan` |
| Роль координатора / организатора | `organizer_role` | `motivation`, `experience`, `plannedContribution` |
| НКО | `organization` | `volunteerTasks`, `supportPlan` |
| Вступление в университет | `university_membership` | `faculty`, `studyYear`, `motivation` |
| Заявка на участие в мероприятии | `event_participation` | `motivation`, `experience`, `availability` |
| Жалоба | `report` | `evidence` |
| Историческая заявка НКО | `legacy_organization` | Только имеющиеся сведения, без выдуманного заполнения |

Общие данные формы передаются отдельно:

```json
{
  "applicationDetails": {
    "formVersion": 1,
    "answers": {
      "motivation": "Хочу координировать экологические акции в районе",
      "experience": "Участвовал в трёх субботниках, организаторского опыта нет",
      "plannedContribution": "Ежемесячные уборки с инструктажем и распределением задач"
    }
  }
}
```

Заявка на роль, автоматически созданная при регистрации, сначала может быть без
ответов. Пользователь дополняет её в «Моих сборах». Владелец сбора дополняет анкету
на странице управления сбором, включая исправления после отказа. Создаётся новая
версия; старые ответы сохраняются. Клиенты без новой анкеты остаются совместимыми,
но неполные анкеты не попадают в обучающую выборку по умолчанию.

## Что отмечает проверяющий

В интерфейсе рассмотрения задаются:

- итог: `approved` / `rejected`; для жалоб `upheld` / `dismissed`;
- `reasonCode`: `complete_and_valid`, `missing_details`, `eligibility_not_met`,
  `verification_failed`, `duplicate`, `safety_concern`, `out_of_scope`, `other`;
- результаты проверки конкретного вида заявки: `passed`, `failed`,
  `not_applicable`, `not_checked`;
- `certainty`: `certain` или `needs_second_review`;
- текстовое пояснение; при отказе оно также передаётся в существующее поле причины;
- номер просмотренной версии `submissionRevision`.

Для НКО сохраняются существующие отдельные подтверждения проверки регистрации и
полномочий. Анкета и разметка не заменяют саму проверку документов.

Если пользователь изменил анкету после открытия окна рассмотрения, решение со старым
номером версии отклоняется с `409`. Выдача роли / изменение статуса откатываются
в той же транзакции. Проверяющий должен открыть актуальные ответы и рассмотреть их.

При Microsoft-подтверждении членства сохраняется решение `actor_type=system`.
Так же отделяется автоматическое закрытие заявки на роль после одобрения НКО.
Это не ручные эталонные решения. Старые API и массовые действия без индивидуальной
разметки сохраняются в журнале с недостающими признаками качества, а не получают
автоматически придуманные причины.

## Хранение в БД

`review_submissions` — версии входных данных. Главные поля:

- `kind`, `source_id`, `revision`: уникальная связка вида, исходной записи и версии;
- `schema_version`, `form_version`: версии формата;
- `snapshot`: снимок полей заявки и нужного контекста на момент подачи;
- `details`: именованные ответы анкеты;
- `applicant_context`: зафиксированные тогда роль, город и агрегаты опыта;
- `input_digest`: SHA-256 канонического содержимого для устранения одинаковых версий;
- `origin`: `live`, `legacy` или `demo`;
- `submitted_at`, `captured_at`: время подачи версии и фиксации.

`review_decisions` — журнал решений с FK `submission_id`. Хранятся итог, проверяющий,
тип автора, код причины, пояснение, уверенность, проверки, просмотренная версия,
версия таксономии и время. Повторное решение не перезаписывает старое. При разных
итогах для одной версии запись помечается как конфликтная и исключается из обучения.
Для разрешения таких конфликтов понадобится отдельное согласованное арбитражное
решение; экспорт сейчас не выбирает одну сторону как истину.

Данные собираются в транзакции с доменными записями через SQLAlchemy unit of work.
Ошибка и rollback откатывают и заявку, и журнал. Условный SQL UPDATE заявки НКО
дополнительно вызывает общий сервис фиксации решения. Обычные записи и решения
фиксируются автоматически, включая вступление через Microsoft, регистрацию
организатора и повторную подачу. Изменение ролей внутри сбора тоже меняет снимок.

Признаки заявки не содержат результата рассмотрения, комментария проверяющего,
актуального статуса или будущих показателей пользователя. Условия мероприятия
для заявки волонтёра сохраняются на момент подачи, а не читаются заново при экспорте.
Промежуточные версии формы, у которых нет решения, остаются неразмеченными.

Снимки и решения защищены от изменения и удаления через ORM. В них намеренно нет
каскадного FK к исходной заявке или аккаунту: история не исчезает при удалении
исходной карточки. Это не замена регламенту хранения: ограничение доступа,
срок хранения, удаление по применимому регламенту и резервные копии настраивает оператор.
Прямые SQL-изменения исходных таблиц не проходят через ORM-журнал; миграции и ручные
операции нужно документировать отдельно.

## Установка

После обновления кода выполните из `backend`:

```sh
flask db-sync
```

Миграция создаёт `review_submissions` и `review_decisions`, сохраняя существующие заявки.
Стандартный production entrypoint уже запускает `db-sync`.

Чтобы видеть существующие записи в общем каталоге данных:

```sh
flask application-data-backfill
```

Команда повторяемая: уже индексированные исходные записи пропускаются. Старые записи
помечаются `legacy`; их нынешнее состояние сохраняется как `legacy_unknown`, если
оно уже содержит результат. Дата, автор и содержание старого рассмотрения **не
восстанавливаются**. Эти записи исключены из обучения.

Для устойчивых псевдонимов задайте `APPLICATION_DATA_EXPORT_KEY` — отдельный секрет
от 32 случайных символов в окружении backend. Например, сгенерируйте его локально
через `python -c "import secrets; print(secrets.token_urlsafe(32))"` и сохраните в
защищённой конфигурации сервера. Не добавляйте секрет в Git или настройки фронтенда.
Один ключ нужен для всех выгрузок, которые планируется объединять. При смене ключа
псевдонимы изменятся. Без ключа экспорт возвращает понятную ошибку; сбор данных работает.

## Выгрузка

В админке появился раздел **«Данные заявок»**: количества по видам, исходам и причинам
исключения, скачивание JSONL для обучения или всех версий. Там нет документов,
контактов и свободного текста.

CLI позволяет выгрузить JSONL либо плоский CSV с манифестом рядом:

```sh
flask export-application-data --output applications-v1.jsonl
flask export-application-data --training-only --output training-v1.jsonl
flask export-application-data --format csv --kind organizer_role --output roles-v1.csv
```

Файлы не перезаписываются. Порядок: `kind`, `source_id`, `revision`. Манифест содержит
версии схем, словари, количество строк и точный набор колонок признаков.
Времена экспортируются в UTC с суффиксом `Z`.

Формат строки JSONL:

```json
{
  "schemaVersion": 1,
  "formVersion": 1,
  "submissionKey": "устойчивый-псевдоним-версии",
  "kind": "organizer_role",
  "caseGroup": "устойчивый-псевдоним-исходной-заявки",
  "applicantGroup": "устойчивый-псевдоним-заявителя",
  "revision": 1,
  "submittedAt": "2026-11-05T10:00:00Z",
  "origin": "live",
  "features": {
    "answers.motivation.length": 57,
    "applicant.events_attended": 3,
    "category.requested_role": "coord"
  },
  "trainingEligible": true,
  "exclusionReasons": [],
  "label": {
    "outcome": "approved",
    "reasonCode": "complete_and_valid",
    "certainty": "certain",
    "checks": {"motivation": "passed", "experience": "passed", "scope": "passed"},
    "actorType": "human",
    "reviewedRevision": 1,
    "reviewerGroup": "устойчивый-псевдоним-проверяющего",
    "decidedAt": "2026-11-05T11:00:00Z",
    "taxonomyVersion": 1
  }
}
```

Без дополнительных флагов произвольные строки превращаются в длину и наличие;
значения сохраняются только для разрешённых категорий, чисел и булевых признаков.
ФИО, телефоны, email, БИН, адреса, изображения и содержимое студбилетов не экспортируются.
Идентификаторы заменяются HMAC-псевдонимами. Это псевдонимизация, а не обещание полной
анонимности: редкие сочетания признаков тоже требуют оценки перед передачей данных.

Для подготовки текстовой модели доступен отдельный CLI-флаг:

```sh
flask export-application-data --include-private-text --output text-for-deidentification.jsonl
```

Он добавляет `privateTextForDeidentification` со снимком текстов, ответами и заметкой
проверяющего. Контактные колонки и документы всё равно не добавляются, но пользователи
могут написать персональные сведения внутри произвольного текста. Такой экспорт нужно
хранить отдельно, вручную обезличить и проверить допустимость использования перед
обучением или передачей за пределы среды оператора. Через веб-интерфейс этот режим
недоступен. CSV дополнительно защищает строки от исполнения как формул в таблицах.

## Правила будущего обучения

`--training-only` оставляет живые анкеты с заполненными вопросами и ручным решением,
привязанным к просмотренной версии: полный код причины, все проверки, уверенность
`certain`, классифицированный итог и отсутствие конфликтов или противоречивого одобрения.
Нерассмотренные, автоматические, архивные, демонстрационные, неполные и сомнительные
записи сохраняются для аудита, но не используются как надёжная разметка.

1. Обучайте задачи по `kind` отдельно либо явно включайте вид заявки в модель.
   Модель будет воспроизводить решения проверяющих; это не доказательство
   объективной правильности каждого решения.
2. Вход модели — `features`; цели — `label`. Времена решений, комментарии,
   уверенность, проверки и причина относятся к разметке, а не к входным признакам.
3. Не разносите связанные версии в train/validation/test. Учитывайте одновременно
   `caseGroup` и `applicantGroup`: например, сначала объедините связанные записи
   в компоненты по обоим ключам, затем делите группы. Для агрегированных жалоб
   в одном деле могут быть разные заявители.
4. Отдельно оцените качество на более позднем периоде; не переносите будущую историю
   пользователя в прошлые примеры. Не используйте случайное разделение отдельных строк.
5. Проверьте доли классов, достаточность примеров по каждому виду, согласованность
   проверяющих и ошибки на разных группах. Флаг `trainingEligible` означает качество
   оформления записи, а не достаточность всего датасета или готовность модели.
6. При будущем подключении храните рекомендации модели и версию модели отдельно от
   человеческой разметки. Автоматические ответы не должны становиться эталоном сами себе.

API для администраторов:
`GET /api/admin/application-data/schema`, `/stats`, `/export`,
`/<kind>/<id>/history`. История конкретной заявки на участие также доступна её
организаторам, а история вступления в вуз — назначенному координатору вуза.
Изменение собственной ожидающей анкеты: `GET/PATCH /api/application-data/<kind>/<id>`.

Основной контракт — `services/review_schema.py`; снимки и транзакционные обработчики —
`services/application_data.py`; правила качества и экспорт — `services/review_export.py`.
Новый вид заявки добавляйте в эти реестры вместе с формой, проверками, сериализацией,
разрешениями и тестом полного цикла. Изменение смысла вопросов или меток требует новой
версии формы / таксономии; не переопределяйте старые значения.
